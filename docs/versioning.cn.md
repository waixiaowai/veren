# 版本号命名与升位规范

> 管的是「发布版本号本身」：格式、升位、预发布、tag。依赖声明放哪
> （`engines.dsh` / peer / dev / dependencies）见
> [dsh-plugin-versions.cn.md](dsh-plugin-versions.cn.md)——两篇互补，不重叠。

## 1. 格式

SemVer：`MAJOR.MINOR.PATCH`，高风险变更可加预发布后缀 `-rc.N`（`2.1.0-rc.1`）。
**不带** build 元数据、不带 `beta/alpha` 字样（DSH 生态的预发布惯例只有 `-rc.N`，
与其保持一致）。

## 2. 单版本线（release train）

**所有 `@veren/*` 包共用一个版本号，统一升位**（现状：2.0.x 线，79 包同号）。
理由：它们是同一个应用的插件族，一起发布（`market/release.mjs` 按闭包拓扑
发布）、一起装进 profile、互相以 `workspace:^`/registry 区间引用——拆开版本
只会让「哪个包配哪个包」变成猜谜。

- 升位一律全族一起动（bump 脚本把 79 个 manifest 改齐 + lockfile 刷新）。
- 禁止单包单独跳号。新包入族：直接取当前线版本。

## 3. 升位规则

| 位 | 什么时候升 | 例子 |
| --- | --- | --- |
| **MAJOR** | 破坏性契约变更：存储域格式不向后兼容、事件/Remote 契约删改、`engines.dsh` 窗口移动（要求新宿主）、卸载/升级路径需要数据迁移 | 2.x → 3.0.0 |
| **MINOR** | 向后兼容的新能力：新工具、新事件、新页面能力、新应用 | 2.0.x → 2.1.0 |
| **PATCH** | 一切其余变更：缺陷修复、内部重构、文档、测试——**因为 registry 不可变，任何内容变更都必须 bump，哪怕只是改一行文档** | 2.0.9 → 2.0.10 |

判断口诀：**让用户数据或宿主契约出问题的 = MAJOR；给用户新东西的 = MINOR；
其余一切 = PATCH。** 拿不准时升 MINOR（保守方向），绝不卡着不升。

## 4. 预发布（-rc.N）政策

只有一类变更**必须**走 rc：**MAJOR（含数据迁移、契约破坏）**。流程：

```
2.1.0-rc.1 发布 → 测试环境浮动跟随 → 预发布环境 pin 到 rc
→ 跑真机清单 + 数据迁移演练 → 通过后发 2.1.0（同号去后缀，不重新起号）
→ rc 期间再改 = rc.N+1；rc 发现破坏性缺陷 = 修完继续 rc，绝不把 rc 转 stable
```

MINOR/PATCH 直接发 stable（预发布环境的演练照走，这是流水线的常设步骤，
与 rc 无关）。

## 5. 两条红线（事故教训固化）

1. **registry 不可变，禁撞号。** 已发布的版本号永不复用、永不覆盖
   （`npm publish` 本身会拒，但**本地/工作树的版本号**必须先 bump 才能
   publish——2026-10-25 的撞号事故：仓库树的 2.0.7 与 registry 已发布的
   2.0.7 内容不同，排查浪费了一小时）。规则：**内容变更 → 先 bump → 再
   publish**，顺序不可逆。
2. **禁跳号、禁回退。** 版本号只前进；发现发坏了 = 发 PATCH 修复版 +
   预发布环境回滚 pin（见 docs/environments.cn.md 流水线），不是重发同号。

## 6. 与其他版本面的关系（三个版本面互不混用）

| 版本面 | 归谁管 | 例子 | 规则 |
| --- | --- | --- | --- |
| `@veren/*` 包版本 | 本规范（单版本线） | 2.0.10 | 上面全部 |
| `engines.dsh` 契约 | DSH 宿主的兼容窗口 | `>=0.2.1-rc.2 <0.3.0` | 独立于包版本；包版本升位**不代表**宿主兼容变化，窗口移动才代表（且那必是 MAJOR） |
| harness 版本 | deepseek-harness 仓自己的线 | 0.2.1-rc.2（`687f282e86`） | 独立演进；预发布签发记录**必须**记 harness commit（插件 pin 管不到共享源码的宿主） |

另：应用定义（`APP_DEFINITION`）里出现的 `version: '0.0.0'` 是历史残留，
新应用一律取所在包的版本号；待统一，不新欠债。

## 7. 提交与 tag 约定

- 版本 bump 单独成笔：`chore(release): 2.0.11 - <一句话主题>`（先例：2.0.9 /
  2.0.10 两笔）。
- 发布提交打 tag `v<version>`（`v2.0.10`），tag 与签发的 RELEASE-NOTES 条目
  互相引用。
- 签发记录：`deepseek/.dsh-staging/profiles/web/RELEASE-NOTES.md`（追加式，
  流程见 docs/environments.cn.md）。

## 8. 环境对齐（版本号在三套环境的读法）

| 环境 | 读法 |
| --- | --- |
| 测试（3080） | `^2.0.x` 浮动，每次发布自动跟随——它是新版本的第一个读者 |
| 预发布（3100） | **精确 pin**（如 `2.0.10`）——签发的版本就是用户将拿到的版本 |
| 正式（桌面市场） | 用户自己升级——agent 的职责到签发为止 |
