# ADR：一个微信管理多台 DSH 设备——云端消息中枢（im-hub）

> 状态：已采纳（2026-10-27）。尖刺验证期；尖刺闸门见 §6，全部通过前本决策对生产通道不生效。
> 英文版：[im-multi-device-hub.md](./im-multi-device-hub.md)。
> 前置事实：[iLink 账号生命周期](./im-account-lifecycle.cn.md)、[消息队列语义](./im-message-queue.cn.md)。

## 1. 问题

一个用户有多台设备装有 DSH，但一个微信同时只能有一个 iLink 会话（bot）——bot 挂在哪台
设备，微信就是那台设备的入口。今天（2.1.8）的答案实质上是「最后扫码的那台设备赢，
其余设备的通道被服务端作废」。多设备场景需要一个显式架构。

## 2. 铁律与证据

| 事实 | 证据 |
| --- | --- |
| 一个微信同时只能有一个 iLink 会话 | 用户确认（协议已知条件）；历次扫码旧 bot 即失联的实测（账号生命周期文档 §1） |
| 重新扫码铸造新 bot，token 绑定 bot | `get_qrcode_status=confirmed` 载荷（流量捕获）；「会话漂移备份」因此不可行 |
| 协议为纯 HTTP/JSON（无公开文档） | 官方 ClawBot 拆解与社区网关（weixin-ilink-gateway 等）——云端网关是 iLink 生态的成熟形态 |

## 3. 备选方案与裁决

| 方案 | 裁决 | 理由 |
| --- | --- | --- |
| 每设备一个 bot（多 bot 共存） | **否决** | 与「一号一会话」铁律冲突；且 2.1.6 起同 owner 退役机制会主动清理兄弟 bot |
| 家中常开设备做中枢 | **否决（本期）** | 中枢离网微信即断；无备份可能（会话漂移不可行）；外网设备回连需额外隧道 |
| 会话漂移备份（断网时云接管） | **否决（永久）** | token 绑定 bot：接管 = 重新扫码 = 换 bot 号，不是备份是迁移 |
| agent 联邦（不路由消息、路由能力） | **推迟** | 跨设备 agent 协作是独立的大能力；先解决消息到达 |
| **CMS 云端中枢（im-hub）** | **采纳** | 单会话挂云端 7×24 在线；设备出站接入（零端口暴露）；离线由云端排队兜底；CMS 有成熟部署管线（systemd + CI/CD 138） |

## 4. 决策

```
微信 ⇄ iLink 服务器 ⇄ 【im-hub（云端，唯一 iLink 会话持有者）】
                          │  ① 设备注册（deviceToken 校验）
                          │  ② 出站长轮询投递（设备离线时云端排队）
                          │  ③ 回复接收 → sendmessage 发回微信
                          ▼
              多台 DSH 设备（每台一个 hub provider 插件）
              设备侧零新机制：hub 只是又一个 provider，
              2.1.8 的队列/私有会话/人员/采集原样生效
```

- **唯一 iLink 会话**挂 im-hub：QR 授权一次，凭据与游标持久化在云端数据目录（0600）。
- **设备接入**：出站 HTTP 长轮询（与微信监视器同构），无需任何入站端口；尖刺期用
  共享 deviceToken 认证，正式版接 device-id 插件（每设备独立身份）。
- **路由**：默认设备（env `HUB_DEFAULT_DEVICE`）起步；指令切换（/device）与内容路由
  是后续项，本期不做。
- **离线语义**：设备不可达时消息留在云端设备队列（至少一次），设备回归后按 cursor 补投。

## 5. 后果

- 消息过云（隐私注记）：正文经 CMS 主机中转；自托管部署下主机即用户自有。
- CMS 主机成为微信通道的单点依赖：im-hub 进程挂 = 微信通道断（消息在 iLink 侧暂存，
  进程恢复后长轮询继续；iLink 离线重放不保证，队列侧以 cursor 尽力补齐）。
- 协议客户端单源：`@veren/im-wechat` 增加 `./api` 子路径导出，云端与插件共用同一份
  5 端点客户端，协议改动一处生效。

## 6. 尖刺闸门（全部通过前不接管生产通道）

1. 一条真实微信消息全程闭环：手机 → hub → 设备长轮询 → DSH 队列消费 → 回答经 hub
   sendmessage 回手机。
2. 3 连消息按序三回（忙碌 ack 生效）。
3. 杀设备侧 DSH 进程 → 消息在 hub 排队 → 重启后补投送达。
4. 终态审计：hub 设备队列文件 + 设备 `messages` 表，每条 message_id 有结局。

## 7. 迁移序列（尖刺通过后执行）

1. 部署 im-hub 至 CMS 主机（systemd 单元，仿 cms.service）。
2. 云端扫码授权（新 bot、owner=同一微信人）→ 旧 bot 被服务端作废。
3. 3080 的 wechat 监视器收到 `-14` 三败自动停止（现有机制），hub provider 已接管；
   wechat 插件不卸载（休眠无害），正式版随配置面清理。
