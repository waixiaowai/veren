# 核心业务识别（二八原则）

按二八原则，约 20% 的模块承担约 80% 的产品价值。方案必须在逐模块展开之前显式识别核心业务，并对核心域显著加深设计密度；禁止全部模块平均用力——识别不出核心域的方案视为结构认知不足，须返回重析。

## 判定三判据

一个模块（或域）必须命中判据①，且命中②③之一，方可进入核心清单；三判据不全者不得入列：

1. **主链不可缺**：沿一条核心业务流追踪完整调用链，该域在链上，缺失则主流程断裂。
2. **失守即失格**：该域失效时产品失去立身之本（如安全边界、事实权威、一致性根基）。
3. **砍余仍可用**：假设其余模块全部砍去，仅留该域与最简入口，产品仍是完整可用的。

## 识别方法

1. 选一条核心业务流（一次典型用户主操作）追踪完整调用链，链上全部域列为候选。
2. 用三判据逐一裁决候选域，剔除不达标者；裁决存疑的域记入 review.md。
3. 核对比例：核心数 ÷ 模块总数 ≈ 20%（0.1–0.4 区间可接受）；偏差过大时在 review.md 说明原因（如模块划分粒度过粗或过细）。
4. 把「核心域清单表」写进总体方案与架构章：列 = 模块、承担的价值、命中判据、关键设计决策（铁律级，如「准入与执行分离」「先权限后执行」「先落库后分发」）。

## 深化要求（核心域 vs 外围域）

以下要求对核心域模块章强制，对外围域不强制：

- 关键设计决策显式成文：每域列出铁律级决策及违反后果，不散落在功能清单里。
- 伪代码必须覆盖失败分支、幂等与恢复策略；纯成功路径的伪代码视为不合格。
- 验收标准不少于 4 条，且至少含一条失败/拒绝路径与一条恢复/幂等路径。
- 时序图标注核心链路（发起方、接收方、失败分支齐全）。

## 与其他章节联动

- 追溯表中属核心链路的需求行加「核心」标记，核心需求与验收项必须双向覆盖。
- review.md 记录：每域命中判据的简证、比例核对结果、判定存疑的域与原因。
- 外围域模块章可简写（契约与验收条数从简），但须在章首或清单表声明其外围定位，不得静默减配。
