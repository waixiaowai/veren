# 方案结构

## 封面

依次包含：一句话概括项目做什么；一段话说明目标用户、痛点与要解决的问题；一段话说明核心架构。核心架构段遵守主技能中的禁用项目名、技术栈与源码引用约束。

## 目录

提供可点击的内容目录与交付文件目录树。目录链接指向实际章节和文件；源码目录只能在确有必要时另列，不能代替方案目录。

## 总体方案与架构

先说明系统边界与外部参与者，再列出全部模块及职责、依赖和数据流。明确哪些调用同步返回、哪些通过事件异步推进、哪些模块拥有数据及状态变更权；仅在实际需要时引入这些机制。文字与 Mermaid 节点、连线、方向保持一致，连线标注调用、数据或事件含义。不要以技术选型列表代替架构。存在跨模块异步推进、事件编排或多步补偿时，另附时序图（`sequenceDiagram`），标注发起方、接收方、消息语义与失败分支。

### 功能模块划分

每个模块单独成节或成文件，按以下顺序展开：

1. 一个英文单词作为模块名，一句话交代职责边界，并说明与相邻模块的分界。
2. 一段话列出完整功能清单，包括主要业务规则、状态和协作对象。
3. 使用 TypeScript `interface` 定义输入、输出及关键实体；使用 `abstract class` 定义抽象方法。标明字段类型、必填性、枚举、标识符、时间和数量单位；不以 `any` 隐藏重要契约。明确错误返回或异常约定。
4. 先用一句话说明伪代码用途，再给出入口函数及类方法调用，以显式参数说明业务流程、分支、返回值和失败处理。涉及副作用时，说明权限检查与关键状态更新顺序；存在重复提交或部分失败风险时，说明幂等与恢复策略。
5. 最终验收标准：给出前置条件、操作、可观察结果，覆盖主要成功、拒绝及失败路径；性能或容量指标只使用已知要求或标记为待确认的目标。

契约和流程结构示意（名称与内容须替换，不能直接作为完成结果）：

```ts
interface SubmitInput { actorId: string; itemId: string }
interface SubmitOutput { id: string; status: "accepted" | "rejected" }
abstract class Submission {
  abstract submit(input: SubmitInput): Promise<SubmitOutput>;
}
async function main(service: Submission, input: SubmitInput): Promise<SubmitOutput> {
  return await service.submit(input);
}
```

### 服务端接口设计

给每个接口稳定标识，一句话说明用途，再定义：所属模块、路径、方法、协议、身份认证及角色/资源级权限、请求参数、响应结果与错误。请求区分 path/query/header/body，列明字段类型、必填性、校验、默认值和示例；响应说明状态码、结构及错误语义。分页、筛选、排序、幂等、版本或流式事件仅在相关接口中明确。

前端使用的每个接口必须在此有定义；字段与模块契约一致。内部类方法不自动等于对外 API；不为了凑章节把每个方法都暴露为接口。没有服务端的项目须给出不适用理由。

### 权限与多主体

先确定“主体”的定义：承担数据归属与权限判定的单位，可以是个体账号、组织、租户、系统进程或外部集成方。列出主体类型、数据归属字段、是否允许切换主体、跨主体可见性的判定规则；多主体并存时说明默认主体如何确定。

再给出一张权限矩阵，作为接口、页面和组件三处权限描述的唯一来源，列为角色、资源、操作、判定、条件。判定只能取允许、拒绝、条件三种；条件需写明判定所依据的数据字段。同一能力不得在接口章写允许而在页面章写不可用。

数据隔离须写明：查询默认附加的主体范围、越权访问返回的统一失败码、切换主体后会话状态与缓存和分页游标如何失效、跨主体聚合是否出现在列表与统计中。

### 错误码与状态模型

给出全局错误码表，列为码、含义、触发条件、是否可重试、用户可见文案、归属模块。接口只引用码，不重复定义语义；同一失败在不同接口下必须用同一码。

状态数量达到三个及以上的实体，须给出状态转移图（Mermaid `stateDiagram-v2`）：节点使用状态枚举值，边上标注触发动作、执行者与判定条件。同时列出非法转移及其失败码，并与错误码表一致；不得只列状态枚举而无转移约束。

### 数据字典

集中列出关键实体的字段：字段标识、类型、必填性、取值范围或格式、默认值、单位、所属主体与可见性。模块契约引用字典中的字段，不重复定义同一字段；同一字段在不同模块中的类型与必填性必须一致。

### 产品原型

先列出产品端总数、各端服务的人群、设备或入口、权限和边界。产品端按独立用户体验划分，不直接把角色数当端数。

逐端列出所有页面：页面标识、路由、一句话功能边界、可用角色、主要操作、关键展示区域和状态。用页面流转表或图描述来源、触发动作、目标及返回行为；覆盖入口、详情、编辑、提交后跳转与无权限路径，避免孤立页面。

用可交互页面或线框展示核心路径；明确演示数据与真实能力的界限。方案阅读页的导航不能代替产品自身的原型设计。

## 系统验收标准

定义整套系统最终验收条件，不分期。每项有编号、场景、前置条件、操作、预期结果和验证方式；覆盖端到端业务、跨模块契约、权限、异常恢复、页面状态恢复及适用的非功能目标。权限部分至少覆盖越权拒绝、跨主体不可见与切换主体后的状态失效；状态部分至少覆盖一次非法转移被拒绝并返回对应错误码；界面部分至少覆盖页面四态、键盘可达与目标语言下的布局。

建立“需求 → 模块 → 接口/页面 → 验收项”追溯表，固定四列：需求标识、实现归属、接口或页面标识、验收项标识。每个需求至少对应一个验收项，每个验收项至少回指一个需求；无法建立对应的行须就地标注原因，不能把模块验收简单重复粘贴成系统验收。

## 专用名词

统一列出业务名词和实体：中文名、统一标识、简短解释及容易混淆的边界。所有状态名称和实体关系与正文一致。

## 技术术语表

单独列出实际使用的技术术语及简短解释，必要时补充在本方案中的用途。不要加入正文未使用的术语充数，也不要与业务名词表混用。
