# 项目方案设计

将需求或现有项目整理为先总后分、可追溯、可验收的中文设计方案。交付的是方案与可渲染的 Markdown；阅读页面由 Astro 站点承担，用 `scripts` 的 build/check/dev 构建、检查、预览。不要把文档任务扩展成业务系统开发。

## 工作方式

1. 确认目标项目、需求来源、现状和输出目录。可以读取已提供的项目资料或源码理解事实；区分已实现事实、拟议设计与待确认假设。缺少目标项目时先询问，不凭空编造。普通设计选择可明确假设后继续，影响核心边界的未知项应询问。
2. 建立统一的模块、实体、接口、产品端、页面、组件和状态命名清单。以清单贯穿各章节，避免同物异名、重复职责及无归属接口。随后按二八原则识别核心业务：读取 [核心业务识别](references/core-8020.md)，以判定三判据产出核心域清单与深化点，先定核心再展开逐模块设计。
3. 按 [方案结构](references/solution.md) 编写封面、目录、架构、逐模块设计、接口、权限与多主体、错误码与状态模型、数据字典。每个 Markdown 文件先写 frontmatter（字段见 [Astro 导入](references/astro.md)），正文不写 H1。
4. 编写 UI 与四层组件设计时，读取 [界面与组件](references/components.md)：覆盖微交互、微文案、无障碍、国际化与页面多态。即使设计不涉及界面，也保留对应章节并说明不适用的依据，不虚构产品端。
5. 编写可用性与验收章节时，读取 [可用性检查与指标](references/usability.md)：逐产品端列出核心任务、可观察的成功判据与可复算的指标阈值，按阶段选择检查方法（启发式自检、任务测试、标准化量表、上线后行为数据）。不涉及界面时保留该节并写明不适用依据，不虚构任务与指标。
6. 交付前读取 [交付与校验](references/delivery.md) 与 [Astro 导入](references/astro.md)，按契约输出 Markdown（frontmatter、英文标题、自动锚点、站点路由链接、预渲染 Mermaid）。用 [scripts](scripts/README.md) 的 `check` 校验内容、`build` 构建站点、`dev` 本地预览；脚本不可用时按 `astro.md` §10 手工核对，并在 `review.md` 记录未验证项。
7. 界面设计须覆盖微交互：定义触发条件、变化属性、时长曲线、可中断性与降级行为。不涉及界面时保留该节并说明不适用依据。
8. 章节编号与英文标题一次定稿后不再改动；标题不写 `{#id}`，锚点按 github-slugger 规则派生；正文链接与 Astro 深链共用同一锚点。

## 表达约束

- 封面的核心架构段和总体方案与架构的说明，不写技术栈、不引用源码、不写项目名。按职责、数据流、控制流和边界清楚表述，保留必要的核心技术术语。此限制不禁止后续使用用户要求的 TypeScript/TSX 契约与伪代码。
- 每个模块以一个英文单词命名，再用一句完整的话说明职责边界；不要用单个英文词代替职责说明。
- 按二八原则分层用力：核心域的功能设计必须显式深化（铁律级设计决策、失败分支、恢复与幂等），外围域允许简写并声明外围定位；禁止全部模块同密度铺开。判定与深化要求见 [核心业务识别](references/core-8020.md)。
- 逐模块、逐产品端、逐组件完整展开，不能只写一个示例就省略其余条目。
- 模块验收和系统验收均描述最终完成状态，不划分阶段或里程碑。
- 禁止编写具体业务实现代码。方案中的模块流程、组件和页面全部使用伪代码，在能清楚表达设计的前提下保持最简；`interface` 与 `abstract class` 只定义契约，不展开具体实现。用于原型演示的必要展示代码不受此限制，但不能接入真实业务接口或实现业务系统。
- 伪代码必须表达参数、方法调用、数据流、结果和异常处理；不能用空实现或待办注释冒充设计。示例中的通用名称应替换为项目真实设计名称。
- 各项设计规范按项目实际情况取用，不逐条凑数：确实不适用的写明“不适用”及依据，已适用到的不省略、不用“按规范执行”带过。
- Markdown 必须能直接放入 Astro 内容集合：frontmatter 只允许 `title`、`description`、`sidebar`、`draft`、`lastUpdated` 五个顶层键；正文不写 H1；站内页间链接写相对路由（`./`、`../`，带尾斜杠，不含 `.md`），页内链接写 `#锚点`，禁止根绝对路由 `/design/…`（子路径部署后会失效）。
- 标题只写「编号 + 英文」，中文标题放 frontmatter 与正文首句；禁止 `{#id}`，禁止标题里出现 `&`、`/`、`：`、`?`、`(`、`)` 等会扭曲锚点的字符。
- 图片用相对路径的 Markdown 语法；Mermaid 先渲染为 SVG 再引用，围栏只作为 `<details>` 源码；`.md` 不写 JSX、组件或表达式。
- 不写自定义 HTML 渲染器；不生成 `web/` 或第二份正文。渲染、路由、目录与搜索全部交给 Astro/Starlight，用 `scripts` 的 build/check/dev。

## Mermaid 依赖

总体架构必须输出 Mermaid 架构图。绘图时按技能名从本会话技能清单加载 `design-doc-mermaid`，按其要求生成和验证。该技能不随本技能附带；各机器技能根目录不同，因此只按名字在清单中查找，不写、不猜、不遍历任何本机安装路径。清单中没有该技能时明确说明依赖缺失并继续完成独立章节，不以其他绘图流程冒充已调用，也不把依赖未完成的方案宣称为完整交付。

写图时须遵守：节点标识用英文，中文标签加引号包裹；标签内出现括号、冒号或引号时转义；单图节点超过约二十个拆成子图或分层展开；连线标注调用、数据或事件含义；图必须与正文的模块清单和依赖方向一致。

图必须先渲染为 SVG，再以 `![说明](./assets/diagrams/x.svg)` 引用，并在 `<details>` 中保留图源码；Astro 不负责运行 Mermaid，禁止依赖运行时渲染。
