# @veren/device-id

A Cordis plugin that provides a stable per-machine device ID via the `DeviceId`
service. Use it whenever any component needs a stable machine identifier
(licensing, telemetry, server-side device binding). Skip it when a per-install
random UUID is enough.

## Usage

```ts
import type {} from '@veren/device-id'; // type augmentation

const id = ctx['device-id'].getId(); // stable UUID, cached per process
ctx['device-id'].source;             // 'store-file' | 'registry' | 'fingerprint' | 'fresh'
```

Inject the service token instead when you are a plugin:

```ts
import { DeviceIdToken } from '@veren/device-id';

export const inject = [DeviceIdToken];
export const apply = (ctx: Context) => {
  const id = ctx[DeviceIdToken].getId();
};
```

## How stability is achieved

Resolution happens once per process, through a fallback chain:

1. **Store file** (primary anchor): `%ProgramData%\veren\device-id.json`
   (`~/.local/state/veren/device-id.json` elsewhere). Once written, every later
   generation returns the same id. **This guarantees requirement #2: without an
   OS reinstall the id never changes, no matter how many times it is generated.**
2. **Registry mirror** (`HKCU\Software\Veren\DeviceId`): recovers the id if the
   store file is deleted.
3. **Hardware fingerprint** (best-effort for requirement #1): the id is derived
   deterministically from a SHA-256 digest of the stable hardware tier: SMBIOS UUID and motherboard serial (Windows), DMI product_uuid / board_serial (Linux, root may be needed) or IOPlatformUUID (macOS). Volatile sources such as Windows MachineGuid, the disk serial and Linux /etc/machine-id are excluded (all are regenerated by an OS reinstall); they form a secondary soft tier only. A machine that keeps its hardware
   gets the same id even after the OS - and both anchors above - are wiped.
4. **Fresh random UUID** only if no fingerprint could be collected at all.

The store file also keeps a rolling list of recent fingerprints (capped at 8)
so future migration scenarios can recognize the machine.

## Config

| key         | type     | default                          |
| ----------- | -------- | -------------------------------- |
| `storeFile` | `string` | platform default shown in step 1 |

## Caveats

- Requirement #1 (surviving an OS reinstall) is best-effort by nature: it holds
  when the hardware fingerprint inputs are unchanged. Replacing the motherboard
  and system disk together can change the id.
- `fingerprints` recorded in the store file are informational today (recovery
  uses the live hardware digest); they are kept for forward-compatible audits.
