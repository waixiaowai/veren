## 1. 这东西解决什么问题

DSH 每次启动（Web 界面、桌面端、headless 命令行都算）成功之后，自动帮你做几件事：

- **开一个新会话**：比如每天早上打开 DSH，自动在某个项目目录起一个会话，并把
  "先看一眼昨晚的构建结果" 这句话发过去，它就开始干活。
- **把一个已有会话拉起来热着**，不用你自己去点开。
- **给已有会话发一句话并唤醒它**：适合"每次开机都提醒它继续昨天没收尾的事"。
- **只留一条消息到收件箱、不吵醒它**：适合"安静留言"，那个会话下次自己跑起来时才会读到。

关键点：**每次 DSH 成功启动，每一条"启用"的启动项都会执行一次**，没有任何防抖。
理由是你自己给的：重启会把上一次启动拉起来的会话打断，所以每次启动就该重新触发一遍。
你唯一能拦住它的开关是那条启动项自己的"启用/停用"。

它和 DSH 自带的"定时提醒"（schedule）是两码事：那个按时间，这个按启动事件。
两者互不影响，存储也不在一起。

## 3. 管理工具：名字与用法

挂上之后模型（也就是我）会多出五个工具：

| 工具 | 干什么 |
| --- | --- |
| `startup_create` | 新建一条启动项 |
| `startup_list` | 列出所有启动项，含启用状态、上次执行结果、跑过几次 |
| `startup_update` | 改一条（改名、开关、换动作、换目标、改消息） |
| `startup_delete` | 删一条 |
| `startup_run` | 立刻跑一次（不等下次启动），用来当场验证 |

**你可以直接照着说的话（最省事的四种）**

1. > 给这个会话登记一条启动项：每次 DSH 启动后，给我发一句"检查一下昨天的构建"。

2. > 每次启动 DSH 后，在 `C:\Users\imeep\Documents\cursour` 这个目录新建一个会话，
   > 第一句话是"先跑一遍 pnpm test"。

3. > 把那条叫"早间提醒"的启动项关掉（不是删掉），下次我要用再开。

4. > 列出我所有的启动项，告诉我哪条刚跑过、哪条是停用的。

**要点**

- 名字（`name`）和动作（`action`）是必填的。
- 动作四个：`new_session` / `resume_session` / `message_session` / `queue_message`。
- `message_session` 和 `queue_message` 必须给消息；`resume_session` 不给消息（给了会报错，
  让你改用另外两个）。
- 没有任何"冷却/间隔"参数。要它别跑，就把那条停用（`enabled: false`）。

## 4. 关键取舍：为什么这么设计

### 4.1 触发时机（最容易翻车的地方）

DSH 的"启动成功"信号 `appReady` 有两个特点：**它可能不存在**（嵌入式宿主不提供），
而且**启动器只在整棵树挂载完、Web 服务器开始监听之后提交一次**。

所以触发做成了两条路，两条都能独立跑通：

1. **启动器给了 `appReady`** → 在它提交后触发。这一路刚好满足"等界面真的服务起来了再干活"。
   而且一旦提交过，之后再订阅会**立即回调**——所以 HMR 热更新重载插件后触发会重新生效，
   不会出现"改一次插件功能就消失"。
2. **启动器没给 `appReady`** → 插件装载完成即触发，安静降级，不报错、不抛异常。

两条路**都汇入同一个闩锁**：一个"已激活的服务"只驱动一次，所以同一个实例里两条路先后
都响也只投递一次。而"重新激活"（热重载、重装、Loader 回写配置树）是一个**新的**已激活
服务，它会再驱动一次——这是去掉防抖之后必然会看到的，见 4.3。

### 4.2 递归护栏

所有投递都跑在 `ctx.agents.withoutInitiator(...)` 里，加上上面的闩锁，一共两道：
闩锁保证"一次激活只驱动一次"，无发起者作用域保证"启动项拉起的会话"不会被记成这次触发的
发起者，也就无法再触发同一套逻辑——不会无限套娃。

去掉冷却之后，这两道就是全部的防线。所以测试里专门钉死了：同一个实例里重复提交
`appReady`、以及在同一个实例上再加一次订阅，都**只投递一次**。

### 4.3 没有冷却：每次启动都执行

- **触发路径不再看任何历史**：每次成功启动，每一条 `enabled` 的启动项都投递。
  `lastRunAt`、`lastOutcome`、`runCount` 只作为"发生过什么"的记录留给面板和模型看，
  不再拦任何东西。
- **`startup_run` 也不看历史**：唯一的拒绝理由是 `item_disabled`（停用），
  想跑停用项就传 `force`。
- **`cooldownSeconds` 这个字段废掉了**：1.1.0 写过的行里可能还留着这个键，
  记录 schema 是开放的，读的时候会被丢掉，下一次写入就不再落盘。
  域版本仍然是 1 —— `single` 布局的后端只认**完全相同**的已存版本号，
  升版本会把用户已有的 `startup.json` 直接判成不兼容，而不是迁移。
- **你在活进程里会看到的现象**：重装/热重载插件时，示例项会当场跑一次。
  这不是故障，是"重新激活 = 新的一次驱动"的直接结果。

### 4.4 数据放哪

启动项走 profile 默认存储后端（json），文件是
`$DSH_HOME/storages/startup.json`，**与会话日志、工作区目录完全解耦**。
你删掉工作区文件夹，启动项还在。

## 5. 第二阶段（Web 管理面板）已经留好的接入点

面板要做的事，我这一期已经把数据和服务接口摆好了，不需要返工：

1. **数据就是文件明文**：`$DSH_HOME/storages/startup.json`，
   结构是 `{ unit, global, tables: { items: { "<startup-id>": {…} } } }`，
   字段就是文档里那套（含 `enabled`、`lastRunAt`、`lastOutcome`、`runCount`）。
   面板即使不调服务，也能直接读这个文件渲染。
2. **宿主服务是 Typert Remote**：服务名 `startupAutostart`，线上命名空间 `startup`，
   已暴露五个远程方法：`catalog` / `create` / `update` / `delete` / `run`。
   面板走 `ctx.remote.startup.*` 即可，语义和工具完全一致。
3. **变更通知**：任何一次写入落地后都会发 `startup-autostart/changed` 事件，
   面板按需订阅即可刷新，不用轮询。
4. **视图字段现成**：`catalog()` 返回的每条已经带好 `enabled`（下次启动会不会执行）、
   `lastRunAt`、`lastOutcome`、`runCount`，面板不用自己算。
