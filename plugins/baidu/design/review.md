## 17. Review

本章记录**实际做过的校验**与**尚未确认的事项**，不把"设计已描述"当作"系统已验收"。校验覆盖本方案文档与方案站点本身；被设计的系统是否达标，由第 14 章验收项在真实环境中判定。

### 17.2 Known Gaps

以下落差是**现状事实**与**目标设计**之间的差异，已在本方案对应位置就地标注；它们不是文档错误，而是需要排期修复的实现问题。

| 编号 | 现象 | 依据 | 影响 | 建议 |
|---|---|---|---|---|
| D-01 | 技能包要求命令版本 3.8.9，安装脚本固定 3.8.4 | 技能说明的版本声明与安装脚本内的版本常量 | 新装用户装完即触发版本不匹配 | 安装脚本版本与技能要求同源生成，发布时校验一致 |
| D-02 | 命令输出存在三种形态（统一信封、裸对象、顶层数组/列表） | 命令参考中 `ls`、`search`、`transfer`、`share` 与其余命令的结果位置不同 | 调用方需逐命令记忆字段位置，链接漏展示的主要成因 | 按 3.2 节统一信封迁移，旧字段保留一个周期 |
| D-03 | 协议工具存在重名：文本上传与链接上传同名 | 工具表中两行同名 `file_upload_by_url` | 宿主侧工具选择歧义 | 为文本上传分配独立工具名，或合并为带类型参数的单工具 |
| D-04 | 正文检索的链接字段与其他命令不同 | `data.hits[].file_url`，无 `return_markdown` | 通用展示逻辑会取空，导致"有命中无链接" | 统一链接字段命名，或在网关侧补预渲染字段 |
| D-05 | 仓库目录名与 README 不一致 | README 写 `skills/baidu-netdisk`，实际为 `skills/baidu-drive`；参考文档路径同 | 新人按 README 找不到文件 | 更新 README 与文档内相对链接 |
| D-06 | 开发库文档中的错误号含义与代码常量冲突 | 一处写 `-7` 为"文件或目录不存在"，代码常量为"文件名不合法" | 排障时误判 | 以代码常量为准统一文档 |
| D-07 | 转存任务查询没有公开子命令 | 命令参考只有提交与结果返回，查询行为描述为内部轮询 | 调用方无法主动查询任务 | 明确任务查询接口，或说明查询仅由命令内部完成 |
| D-08 | 路径与凭据判断分散在命令层与行为层 | 行为层有独立路径规则与安全约束，命令层也有路径校验 | 规则漂移风险 | 收敛为单一实现（P-03），行为层只引用错误码 |
| D-10 | 预渲染图使用固定配色、白底，不随站点深色主题反转 | Mermaid 主题固定，SVG 内文字为深色 | 深色主题下图为白底卡片，观感与正文不一致但可读 | 若需双主题图，需渲染两套并按主题切换 |
| D-11 | 站点默认引用 `/favicon.svg`，生成站点未提供该文件，访问时 404 | 静态产物访问日志 | 仅控制台报 404，页面与内容不受影响 | 在站点模板的 `public/` 放入 favicon，或改站点配置指向内容侧图标 |
| D-09 | 记忆备份的宿主识别依赖硬编码路径 | 脚本按固定目录特征识别四类宿主 | 宿主目录变更即失效 | 改为配置注入 + 显式声明，未知环境直接拒绝 |

### 17.5 Build and Repro

Markdown 是唯一内容来源，站点由 `scripts/cli.mjs` 同步到 Astro/Starlight 后构建；`design/.design-doc/` 是生成目录，不提交。

```bash
# 内容校验（frontmatter、标题、链接、锚点、资源、语法）
node .agents/skills/project-design-doc/scripts/cli.mjs check design
# 构建（首次加 --install）
node .agents/skills/project-design-doc/scripts/cli.mjs build design --install
# 本地预览
node .agents/skills/project-design-doc/scripts/cli.mjs dev design --port 4321
# 图的重新生成（改过 Mermaid 源码后）
node tools/render-figures.mjs tools/figures design/assets/diagrams
# 产物核对（构建后）
python tools/verify_dist.py
```

图源码同时保留在 Markdown 的 `<details>` 中；改图时必须先改 Markdown、同步 `tools/figures/*.mmd`、重新渲染 SVG，再重跑 check/build，不得只手改 SVG。

### 17.6 Core Domain Evidence

核心判定的依据与比例核对按 [核心业务识别](/design/architecture/#13-core-business-identification) 的三条判据执行；为避免链接歧义，本节直接列出结论。

| 模块 | ①主链不可缺 | ②失守即失格 | ③砍余仍可用 | 结论 |
|---|---|---|---|---|
| command | 命中：核心流必经命令执行 | 未命中：失效表现为不可用而非数据错误 | 命中：仅留命令即可完成文件操作 | 核心 |
| guard | 命中：所有出网请求经其放行 | 命中：路径与凭据失守等于越权与泄露 | 未命中：单独存在无业务入口 | 核心 |
| skill | 命中：Agent 入口的唯一行为层 | 未命中：失效可退回命令直用 | 命中：技能 + 命令构成完整入口 | 核心 |
| bridge | 未命中：并列入口，不是主链 | 未命中 | 命中：协议入口自洽 | 外围 |
| client | 未命中：开发库入口 | 未命中 | 命中：库可独立使用 | 外围 |
| memory | 未命中：增值能力 | 未命中 | 未命中：删去不影响文件主流程（仅失去备份） | 外围 |
| delivery | 未命中：前置条件，不是业务环节 | 未命中：失守表现为不可用 | 未命中：无安装则无入口 | 外围 |

比例：核心 3 / 模块 7 ≈ 0.43，高于 20% 的经验值，原因是七个模块按"入口 + 职责"切分，粒度过细；若把 bridge 与 client 合并为 "entry" 域，比例降到 2/6 ≈ 0.33。判定存疑项：bridge 在"协议宿主是主要入口"的产品形态下可主张命中①，当前按本方案的四入口定位归外围，待产品形态确认后复核（见 17.1 A-01）。
